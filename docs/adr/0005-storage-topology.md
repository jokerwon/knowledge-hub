# ADR-0005：存储拓扑——PostgreSQL（元数据+向量） + MongoDB（正文）

- 状态：已接受（「会话与消息」范围由 ADR-0009 收窄：不持久化）
- 日期：2026-08-28

## 背景

MVP 数据量级为个人数百篇文档、万级切片。ADR-0003 倾向单存储；但决策人明确要求与目标架构的双库边界对齐。

## 决策

- **PostgreSQL + pgvector**：文档元数据、切片记录、向量、会话与消息等全部结构化数据。
- **MongoDB**：文档正文（`document_contents`），按文档 ID 关联。
- 不引入 Elasticsearch、专用向量库、Neo4j、消息队列。

## 曾提出的反对意见（记录在案）

MD/TXT 正文为纯文本，PG `TEXT` 列可承载；引入 MongoDB 增加一个有状态服务，带来 PG 元数据与 Mongo 正文的双写一致性与额外运维成本。决策人知悉后仍坚持，理由为：**与未来目标架构（PG+Mongo 多库）对齐，MVP 即建立双库边界**。

## 后果

- 写入顺序固定为：先写 PG 元数据 → 再写 Mongo 正文 → 切片与向量入 PG；任一步失败将文档标记为 `failed`，允许删除后重传（见 ADR-0008），不做跨库事务。
- docker-compose 需运行 postgres 与 mongo 两个有状态服务。
- 删除文档时必须同时清理 PG 行与 Mongo 正文，删除逻辑集中在文档服务内，禁止分散调用。
